# 10–13 минут. Теперь главное: агент отличается от copilot

Итак, мы подошли к самой интересной точке.

До этого момента мы говорили, что модель может читать документы, анализировать данные, находить аномалии и помогать инженеру.

Но здесь начинается качественный скачок.

Есть большая разница между copilot и агентом.

Copilot помогает человеку выполнять действие.

Агент потенциально способен сам пройти через цепочку действий, используя доступные ему инструменты.

Допустим, инженер приходит с задачей.

Не «напиши мне письмо».

А, например:

«Проверь, почему этот параметр ушёл от ожидаемого диапазона».

Обычный чат-бот может предложить несколько гипотез.

Copilot может помочь написать запрос к базе данных.

Но агентная система потенциально может сделать гораздо больше.

Она может понять задачу.

Потом найти baseline.

Потом найти предыдущие конфигурации.

Потом посмотреть историю изменения.

Потом запросить telemetry.

Потом получить результаты испытаний.

Потом сравнить их между собой.

Потом запустить какой-то вычислительный инструмент.

Потом, если разрешено, обратиться к симулятору.

Потом проверить полученные результаты против требований.

И уже после этого сформировать заключение для инженера.

Вот это принципиально другая архитектура.

Потому что модель перестаёт быть конечным местом, куда человек приходит за ответом.

Она становится частью workflow.

То есть появляется:

**human → agent → knowledge → tools → evidence → recommendation → human**

И именно слово tools здесь самое важное.

# 13–16 минут. Почему MCP вообще интересен

Когда говорят MCP, легко подумать, что это просто ещё один технический стандарт.

Но с точки зрения архитектуры главное не название.

Главное — возможность стандартизировать доступ модели к инструментам.

Представим:

есть модель;

есть база;

есть simulation tool;

есть telemetry system;

есть repository;

есть внутренний API;

есть calculator;

есть test data service.

Без tool layer человек должен сам вручную соединять всё это.

С tool layer модель потенциально получает структурированный способ обращаться к внешним системам.

То есть:

**model → tool**

а дальше:

**tool → system → result → model.**

И вот тут AI начинает напоминать не чат, а операционную систему.

Потому что операционная система в широком смысле — это способ связать вычислительную логику с ресурсами.

AI agent + tools делает похожую вещь:

**интеллект → интерфейс → реальные ресурсы.**

В публичной вакансии SpaceX Vehicle Engineering прямо фигурируют engineering RAG и engineering MCP servers, а также agentic engineering tools. citeturn892097search2

Это очень сильный сигнал.

Не потому, что мы теперь знаем внутреннюю архитектуру SpaceX целиком.

Мы её не знаем.

Но мы видим, что компания нанимает людей строить именно такой класс систем.

И это уже намного глубже, чем «у нас есть LLM».

# 16–20 минут. Представим инженерного агента внутри SpaceX

Давай теперь попробуем мысленно реконструировать сценарий.

И сразу договоримся: это реконструкция, а не утверждение того, что именно такая система уже работает внутри SpaceX.

Инженер говорит:

«Найди причину отклонения».

Агент получает задачу.

Первое, что ему нужно, — контекст.

Он идёт в retrieval layer.

Находит требования.

Находит relevant design docs.

Находит test data.

Находит предыдущие решения.

Потом идёт в telemetry.

Получает реальные значения.

Потом может посмотреть на manufacturing history.

Получает информацию о конкретной конфигурации hardware.

Потом запускает аналитический инструмент.

И в результате возникает уже не просто generated answer.

Возникает evidence package.

То есть:

вот наблюдение;

вот источник;

вот конфигурация;

вот сравнение;

вот anomaly;

вот возможные причины;

вот уровень уверенности;

вот следующий рекомендуемый тест.

И здесь очень важная деталь.

В инженерии ответ ценен не сам по себе.

Ценен **след** от ответа до evidence.

И это совпадает с нашей собственной архитектурной логикой:

**answer без provenance слабый;**

**decision с provenance намного сильнее.**

Поэтому AI engineering system должна хранить не только то, что модель сказала.

Она должна понимать:

**почему она это сказала.**

# 20–23 минуты. Агент не должен быть всесильным

Здесь появляется ещё одна принципиальная вещь.

Если дать агенту слишком много прав, мы создаём опасную систему.

Допустим, у него есть доступ к:

production;

flight software;

hardware configuration;

customer data;

финансовым системам.

Тогда один неверный шаг может иметь огромные последствия.

Поэтому настоящая agentic architecture должна иметь permissions.

Не:

**agent can do everything.**

А:

**agent can do specific things in a specific scope.**

Например:

читать документацию — можно;

строить анализ — можно;

запускать sandbox simulation — можно;

создавать candidate configuration — можно;

изменять safety-critical configuration — нельзя без approval;

вносить irreversible production change — нужен human gate.

И вот здесь возникает понятие **controlled autonomy**.

Автономность не является бинарной.

У неё есть уровни.

Можно дать агенту автономно:

прочитать;

найти;

сопоставить;

рассчитать;

смоделировать;

предложить.

Но не обязательно разрешать:

утвердить;

запустить;

изменить критическую систему;

отправить необратимую команду.

И если посмотреть на это как на архитектуру, становится видно, что permissions — это не административная деталь.

Это часть cognition layer.

То есть:

**what the system knows**

и

**what the system is allowed to do**

должны быть связаны.

# 23–26 минут. AI model — только одна деталь большой системы

Теперь давай сделаем ещё один шаг.

В начале AI-волны все обсуждали модели.

Какая модель лучше?

Какая модель умнее?

Какой benchmark выше?

Для промышленной системы этого недостаточно.

Потому что production AI stack выглядит скорее так:

**data → storage → retrieval → model → inference → tools → application → monitoring → feedback.**

Если модель превосходная, но у неё нет качественных данных, результата не будет.

Если данные хорошие, но retrieval плохой, результат не будет.

Если retrieval хороший, но tool layer слабый, агент не сможет работать.

Если tools есть, но permissions не настроены, появляется риск.

Если всё это работает, но monitoring отсутствует, система постепенно деградирует.

Поэтому настоящая AI system architecture — это цепочка.

И вот здесь мне кажется особенно интересным то, что SpaceX одновременно нанимает специалистов сразу на несколько участков этого stack.

Публичная вакансия Applied AI говорит о проектировании, оценке, deployment и интеграции современных AI systems, включая large language models и agentic systems, и прямо описывает end-to-end lifecycle AI capabilities от prototype до production. citeturn892097search5

То есть опять же:

не только модель.

А **capability lifecycle**.

# 26–29 минут. Inference — скрытая часть революции

А теперь посмотрим на часть, которую обычный пользователь вообще не замечает.

Inference.

Допустим, модель уже обучена.

Но теперь миллионы запросов.

Ты не можешь просто запускать огромную модель отдельно для каждого запроса без оптимизации.

Возникают вопросы:

как распределять GPU?

как балансировать нагрузку?

как объединять запросы?

как кэшировать состояние?

как уменьшать latency?

как повышать throughput?

Как только AI становится массовой инфраструктурой, inference превращается в отдельную инженерную дисциплину.

И именно такой класс компетенций публично фигурирует в вакансиях SpaceX.

Там появляются distributed inference, load balancing, autoscaling, scheduling, KV cache, continuous batching и high-throughput serving.

Это означает, что внутри компании AI рассматривается как service infrastructure.

И здесь снова можно увидеть тот же паттерн, который мы нашли в обычной SpaceX.

В космической системе:

найти bottleneck;

контролировать bottleneck;

увеличить throughput.

В AI-системе:

compute bottleneck;

контроль compute;

увеличение inference throughput.

И это очень красивая симметрия.

# 29–32 минуты. Compute становится инфраструктурой, а не ресурсом

Дальше мы попадаем в ещё более интересное место.

Если AI становится настолько важным, что компании нужен собственный compute, то GPU уже перестают быть просто оборудованием.

Они становятся частью стратегической инфраструктуры.

И тут появляется вопрос энергии.

GPU нужно питать.

Его нужно охлаждать.

Нужно строить дата-центры.

Нужны сети.

Нужны storage systems.

Нужна fiber connectivity.

И получается:

**AI = compute + power + cooling + networking + software.**

И это почти буквально повторяет космическую архитектуру.

Ракета — тоже не только engine.

Есть:

fuel;

ground infrastructure;

range;

software;

telemetry;

maintenance;

logistics.

То есть и здесь появляется одна и та же системная логика.

**Capability определяется не одним компонентом, а согласованностью всех компонентов.**

И для SpaceX это особенно интересно, потому что компания одновременно строит обе системы:

физическую инфраструктуру для запуска,

и вычислительную инфраструктуру для AI.

# 35–38 минут. AI, который улучшает сам AI

Теперь давай немного глубже.

Если есть training infrastructure и reinforcement learning, возникает рекурсивная система.

Есть AI model.

Она используется.

Мы наблюдаем результаты.

Потом используем feedback.

Делаем post-training.

Получаем новую модель.

Новая модель становится лучше в определённых задачах.

Её снова используем.

И цикл повторяется.

То есть:

**AI → feedback → training → better AI → more useful work → more feedback.**

А теперь добавим инженерный контур.

Инженер использует AI.

AI помогает анализировать данные.

Полученные решения создают новые тесты.

Тесты создают новые данные.

Новые данные могут использоваться для улучшения AI.

И появляется двойной цикл:

**AI improves itself**

и одновременно

**AI improves engineering.**

Вот это уже похоже на настоящую cognitive infrastructure.

Не просто модель.

А система, способная постоянно обновлять собственный интеллектуальный слой.

# 38–41 минут. Cursor — почему это важнее, чем кажется

Теперь берём Cursor.

14 августа 2026 года Cursor официально объявил, что был приобретён SpaceX. Там же Cursor указал, что сделка завершает процесс, начавшийся с партнёрства со SpaceXAI в апреле, и что у Cursor появляется доступ к очень крупному GPU fleet SpaceX. citeturn892097search0

На поверхностном уровне можно сказать:

«SpaceX купила AI-редактор кода».

Но это слишком поверхностно.

Посмотри на цикл:

**idea → specification → code → test → deploy → feedback.**

Если AI может участвовать на каждом этапе программного цикла, то скорость разработки software становится частью общей инженерной скорости.

И это очень важно для SpaceX.

Потому что современный spacecraft — это огромная комбинация hardware и software.

Поэтому ускорение software loop может косвенно ускорять:

avionics;

ground systems;

operations;

data pipelines;

AI infrastructure;

simulation;

tools.

Cursor таким образом может быть не просто productivity acquisition.

Это потенциальный **control point над software engineering loop**.

И это очень похоже на старую логику вертикальной интеграции:

контролировать критическую границу,

которая влияет на throughput всей системы.

**PHYSICAL LOOP**

observe → retrieve → reason → act → measure → learn.

**physical loop × cognitive loop.**

Вот это, на мой взгляд, самая интересная архитектурная идея всего исследования.

# 47–50 минут. Starmind: а что будет, если compute выйдет в космос?

И теперь появляется Starmind.

SpaceX публично описывает Starmind как orbital AI compute architecture, где спутники получают локальный compute, солнечную генерацию и high-bandwidth laser links для передачи результатов через Starlink.

На странице SpaceX сейчас указывается compute payload до 250 kilowatts peak и 175 kilowatts average, а сама компания говорит о возможности использовать readily available solar power and cooling in space. citeturn892097search9

Если это когда-нибудь станет operational architecture, появляется новый уровень.

Сейчас:

**Earth → data center → AI.**

Тогда:

**Sun → orbital power → orbital compute → laser links → network → Earth.**

И это означает, что space infrastructure может стать частью AI infrastructure.

Но здесь надо быть особенно аккуратным.

Starmind — это public development concept.

Мы не должны говорить:

«SpaceX уже построила orbital AI data centers».

Это было бы неправильно.

Нужно говорить:

**SpaceX is publicly developing an orbital AI-compute architecture.**

Это факт.

А вот вопрос, насколько быстро и в каком масштабе это станет реальной эксплуатационной системой, — открытый.

# 50–54 минуты. Почему это может быть фундаментально

Представь, что у тебя есть три ограничения:

энергия,

compute,

охлаждение.

На Земле каждое из них может становиться bottleneck.

В космосе солнечная энергия доступна практически постоянно на подходящих орбитах.

Тепло можно отводить radiatively.

И если у тебя есть дешёвый launch и высокая throughput, ты потенциально можешь постепенно добавлять compute в orbit.

Это уже другой тип инфраструктуры.

Но опять же — важно не перепутать архитектурную возможность с доказанной экономикой.

Нам пока нужно будет отдельно исследовать:

mass;

power;

thermal rejection;

chip radiation tolerance;

laser bandwidth;

orbital maintenance;

replacement;

debris risk;

network latency;

capex;

lifecycle cost.

То есть Starmind — это прекрасная гипотеза для исследования.

Но пока не готовый industrial fact.

agents,

**мозг находится в сети взаимосвязанных систем.**

И это уже очень близко к нашему собственному исследованию.

У SpaceX, судя по публичным данным, потенциальная система:

**physical infrastructure → data → models → agents → engineering action.**

И теперь возникает очень интересный симметричный вопрос.

Можно ли построить универсальный cognitive layer, который одинаково хорошо работает:

для человека,

для исследовательской программы,

для инженерной организации,

для робота,

и в конечном счёте для космической инфраструктуры?

Вот это уже не просто вопрос SpaceX.

Это один из центральных вопросов Cosmic Programm.

И здесь я бы остановил наш сегодняшний разговор.

Потому что дальше нам уже не нужен обзор.

Дальше нам нужно делать настоящий reverse-engineering публичной архитектуры.

То есть взять:

**Data**

и выяснить, какие классы данных публично видны.

Потом:

**Model**

и понять, какие модели где используются.

Потом:

**Agent**

и отделить job-posting claims от production evidence.

Потом:

**Tools / MCP**

и восстановить, какие interfaces публично подтверждены.

Потом:

**Inference**

и понять, как устроен compute layer по доступным данным.

Потом:

**Human gate**

и попытаться понять, где проходит boundary autonomous action.

А после этого:

**Feedback**

и посмотреть, как AI включается обратно в engineering lifecycle.

И если нам удастся восстановить эту цепочку достаточно хорошо, мы получим самое интересное:

не список AI-инструментов SpaceX,

а **публичную модель её cognitive engineering architecture**.

И тогда можно будет сравнить её с нашей собственной архитектурой.

Не для того, чтобы сказать:

«мы лучше»

или:

«они лучше».

А чтобы увидеть:

**что работает у них, что работает у нас, чего не хватает у каждого подхода и какие элементы можно доказательно объединить.**

Вот это уже будет следующий уровень исследования.
